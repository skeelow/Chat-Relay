# M1.2 — relay/engine.ts

Task: M1.2 — `relay/engine.ts`: WebSocket server, token check, `hello`, `status`, `captured` handling, writes to the store.
Result: pass

What was built:

- `relay/engine.ts` exports `startEngine(options)` → handle with the bound port, the store and `stop()`. Runs standalone (`node relay/engine.ts`): default port 8787, default db `relay.db`, token at `%APPDATA%\RelayChat\token`. The server is the `ws` package — Node has no built-in WebSocket server, so the task itself demands the dependency; the store still has zero.
- **Token check:** the token file is created with a 32-byte random hex value on first start, read thereafter, and never logged. Every connection must send `{type:'auth', token}` as its first frame (5 s grace); wrong or missing auth closes with 4401, grace expiry with 4400. Comparison is constant-time (`timingSafeEqual`).
- **`hello`:** an adapter registers by participant name — only `codex` and `astra` are valid; anything else closes with 4400. A new connection for the same participant replaces the old one. A successful hello announces initial status `idle` to GUIs. No ack frame: silence = accepted, close = rejected.
- **`status`:** the five SPEC statuses flow to GUI connections as `{type:'status_update', adapter, status}`; a socket close reports `disconnected`.
- **`captured`:** `{type:'captured', body, sourceRef?}` from a registered adapter → `store.insertMessage({source: <participant>, targets: ['user'], body, sourceRef, hop: 0, initialStatus: 'captured'})` → broadcast `{type:'transcript_update', message}` to GUI connections. Duplicate and relay-header rejections from the store are skipped silently — the store is the authority. Captures never appear in `pendingDeliveries` (status `captured` is not a pending status): the read-only room holds nothing to approve or send.
- **Read-only milestone enforced:** `send`, `approve`, `reject`, `set_mode`, `stop` are accepted and ignored; unknown and non-JSON frames ignored. The engine has no `deliver` path at all until M2.2 — nothing can be sent to either AI through it.
- **Local only (hard rule):** binds `127.0.0.1` by default and tests pin it; `0.0.0.0` is never used.

Acceptance checks (M1.2 level; the milestone's 3-second/live checks are exercised end-to-end in M1.5):

- [x] WebSocket server with token check — token generated (64-hex, value never printed), wrong token → 4401, any frame before auth → 4401.
- [x] `hello`/`status`/`captured` handled per the SPEC protocol — registration, unknown-name rejection, status flow + disconnect reporting, capture → store + `transcript_update` broadcast with ULID, contentHash, targets and hop verified.
- [x] Writes to the store — captures land in `messages` (proven via the duplicate rule), duplicates skipped without re-broadcast, nothing ever pending.
- [x] Nothing is ever sent — `send`/`approve`/`set_mode`/`stop`/nonsense frames store nothing, broadcast nothing, close nothing.
- [x] No replay — after an engine restart on the same database, a freshly connected GUI hears nothing from the stored transcript; a live capture afterwards flows normally.

Suite: **20 tests, 0 failures** (13 store + 7 engine).

Files changed: `relay/engine.ts`, `tests/engine.test.ts`, `package.json` (+`ws` dependency, +`@types/ws` devDependency, test script runs both suites with `--test-force-exit`), `docs/status/m1.2.md`.

Design decisions (flagged for the publisher — the SPEC prose implied these but didn't spell them out):

- The auth frame `{type:'auth', token}`: the SPEC says clients "authenticate with a token from %APPDATA%\RelayChat\token" but the protocol table defines no auth message. This is the minimal concrete shape — approve or reshape before M1.3/M1.4 build adapters against it.
- Adapter identity: `hello.name` is the participant the adapter speaks for (`codex` | `astra`); one connection per participant, newest wins.
- Captures are stored with `targets: ['user']`, `hop: 0`, delivery status `captured` — the read-only room's bookkeeping row: not pending, nothing to approve until M2.
- A GUI connection is currently "any authenticated client that never says hello" — fine for M1.5's single window.

Surprises:

- The test runner needed `--test-force-exit`: after tests finish, a lingering socket handle can keep the node --test child process alive on Windows. Also, Windows can hold a just-released temp-dir handle past every rmSync retry; cleanup is best-effort (warned, never fails assertions).
- The one red iteration was a test-helper bug, not an engine bug: an `expectSilence` waiter wasn't removed on timeout, so it silently swallowed the next broadcast (the test then misread the transcript_update as the idle status and starved). Diagnosed by re-running the exact flow with a raw-client probe; fixed by keeping the waiter reference for removal.
