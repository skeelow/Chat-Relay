# M1.3 — Codex adapter

Task: M1.3 — turn the M0.1 spike into an adapter that reports status and completed turns.
Result: pass

What was built:

- `adapters/codex/adapter.ts` — the read-only Codex adapter. It spawns its OWN `codex app-server` (never the desktop app's), handshakes, confirms the ChatGPT login (the auth token is never requested or printed), connects to the relay engine (`{type:'auth', token}` from `%APPDATA%\RelayChat\token`, then `hello` as `codex`), and polls `thread/turns/list` on the configured thread every second **without resuming it** — it never holds the thread's single-writer lock, so the user's own Codex sessions on that thread keep working.
- **Capture:** a turn reaching `completed` → its last `agentMessage` text → engine `{type:'captured', body, sourceRef: turn id}`. The store dedupes across restarts via that sourceRef. Turns are marked seen only after a successful send, so engine disconnects retry instead of losing turns. Completed turns with no reportable final text are marked seen, never captured (no partials).
- **Status:** newest turn `inProgress` or fresh `interrupted` → `streaming`; otherwise `idle`; five consecutive poll failures → `disconnected` once. Only status changes are sent.
- **Read-only by construction:** no `turn/start`, no `thread/start`, no `thread/resume` anywhere in the adapter; codex approval requests are logged and never answered. The spike's write path belongs to M2.2's `deliver`.
- **CLI:** `node adapters/codex/adapter.ts <thread-id> [--engine ws://127.0.0.1:8787] [--token <path>] [--poll-ms 1000]`

Experiment findings (validated before building, per the SPEC's "never guess an API shape"):

- `thread/turns/list` works **without** `thread/resume` and keeps working **while another process holds the thread's writer** — no `-32600`. This is the entire basis of the design.
- A live foreign turn shows status `interrupted` to a non-owner (never `inProgress`): fresh-interrupted therefore reads as `streaming`, with a 180-second window so a genuinely interrupted turn falls back to `idle`. `planPoll` also handles `inProgress` directly if codex ever exposes it to non-owners.
- A brand-new thread with zero turns is **not listable** by another process (`thread not loaded`) until its first turn materializes the rollout on disk; the adapter retries the initial read five times before failing fast.
- Completion visibility: the experiment's poller saw the completed turn ~0.5s after the `turn/completed` event; the live smoke measured 330ms.

Acceptance checks (M1.3 level; the milestone checks are exercised fully in M1.5):

- [x] Reports status — `idle`/`streaming`/`disconnected` flow to the engine; the smoke's GUI sequence was `idle → streaming → idle`.
- [x] Reports completed turns — 8 hermetic tests for the pure `planPoll` logic, plus the live smoke: PONG captured with `source: codex`, `sourceRef` = the codex turn id, delivered to the GUI **330ms** after completion (spec: within 3 seconds).
- [x] Nothing is ever sent — the adapter contains no write calls at all.
- [x] Hard rules — own app-server only; no credential handling (codex auth token never requested; relay token read from the engine's token file per the approved design and never logged); approvals never answered; the PONG test turn ran in a dedicated `thread/start` thread, never a book thread.

Suite: **32 tests, 0 failures** (13 store + 11 engine + 8 adapter logic). Live smoke: pass.
