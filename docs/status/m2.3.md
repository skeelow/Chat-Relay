# m2.3 — GUI: Send to Codex, approval flow, pending count (+ adapter A1/A2)

## Task
M2.3 per the packet: the astra Send-to-Codex button, the D9 status line, the
header pending count, GUI safety rules, and the codex-adapter minors A1/A2.
No protocol/SPEC changes; engine and store untouched.

## Result
- New pure module app/src/deliveries.ts (all GUI decisions, DOM-free): the D9
  status→(label, actions) table; sendButton (astra only; none→Send to Codex,
  failed→Send again, other statuses hidden, other sources never); pendingCount;
  applyDeliveryUpdate (pure, keeps rows for not-yet-shown messages); exact-JSON
  frame builders forward/approve/reject.
- renderer.ts: every astra message gets a footer (status line + buttons), rendered
  from snapshot deliveries + delivery_update only. Clicks send the frames, then
  disable that item's buttons until its next delivery_update; all buttons disable
  while the engine is offline. All text via textContent (error text included).
  Unknown-message updates are kept and applied when the message arrives later.
- index.html: #pending badge ("N pending", hidden at 0) + footer CSS in the
  existing style. package.json: the new test file joined the npm test list.
- Adapter A1: a failed resolveThread is remembered — new delivers fail at once
  with "relay thread not resolved: <error>" instead of buffering until the ack
  timeout; the next config clears the error and retries. A2: a CLI thread id logs
  "relay thread <id> (from command line — saved; later runs reuse it)"; the usage
  comment says the same.
