# m2.2 — Codex adapter `deliver` on the dedicated relay thread (+ E1/E2)

## Task
M2.2 per the packet: the adapter's write path on the relay's own dedicated Codex
thread (publisher decision), settings accessors, config/thread frames, E1+E2.

## Result
- Store: getSetting/setSetting (upsert); the thread id lives in settings.codex_thread_id.
- Frames: engine → codex `config {threadId|null}` right after hello (before any queued
  deliver); codex → engine `thread {threadId}` — stored, accepted from the codex socket only.
- Thread choice (chooseThread, tested): CLI arg > config id > thread/start + thread/name/set
  "Relay Chat". The reader polls the same thread. Deliveries arriving while a fresh
  thread/start is still in flight are buffered and flushed on resolution (a race the first
  smoke run caught — the row failed "relay thread not resolved yet"; fixed, re-verified).
- Writer: thread/resume only when the first deliver arrives (never at startup); the
  subscription is then held for the process lifetime. `delivered` acks as soon as the
  turn/start response succeeds. -32600 / "active writer" → failed "thread busy — close the
  Relay Chat thread in the Codex app, then forward again" (deliverFailureText, tested).
  Never retried. Deliveries run sequentially (one writer, one turn at a time).
- Unsubscribe experiment (dedicated thread, scratch script): thread/unsubscribe returns
  {status:"unsubscribed"} but does NOT release the writer — a second process still gets
  -32600 "already has an active writer" after the unsubscribe, while the unsubscribed
  process can still turn/start. Per the packet: subscription kept; the relay thread cannot
  be typed into in the Codex app while the adapter runs (restart the adapter to release).
- Echo drops (planPoll, tested): a turn whose text starts with `[Relay ·` is marked seen,
  never captured; a capture whose body hash matches a body delivered in the last 10 minutes
  is dropped the same way (hashBody shared with the store). Engine echo filter = 2nd line.
- E1: a late `delivered` upgrades a row failed ONLY with "no confirmation from adapter";
  genuinely failed rows stay failed (tested). E2: a replaced adapter's delivering rows fail
  immediately with "adapter replaced before confirming" (tested).
