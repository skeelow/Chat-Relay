# M0.2 — ChatGPT extension spike

Task: M0.2, `spikes/chatgpt-extension/`: a Manifest V3 extension with one content script on `https://chatgpt.com/*`, logging only (it sends nothing), completion detection by two signals together, and a popup button that types the test prompt without sending.
Result: partial — the extension is built, reviewed, and fixed per the review; all four behavioral acceptance checks need the publisher's logged-in Chrome (the agent cannot load an unpacked extension into the user's browser).

Acceptance checks (mechanisms as fixed — all need publisher verification in the console):

- [ ] Each completed reply is logged exactly once, never mid-stream — a reply logs only if it was WITNESSED streaming this page session (its turn carried `data-talvt-turn-state="in_progress"`, or the stop button was present), and then ALL of: stop button gone, turn state `complete`, text unchanged for 1.5s. Dedupe by `data-dil-message-id`.
- [ ] Code blocks and paragraphs survive intact — the log uses the reply body's `innerText` (paragraph breaks and `<pre>` content survive). Check with a reply containing a code block; note whether the code-block header bar (language name, "Copy code") appears and whether it must be stripped.
- [ ] Reloading the page does not re-log old messages as new — replies that merely appear (reload, sidebar conversation switch) were never seen streaming, so they never log.
- [ ] Typed test text appears in the box and waits for the user — the popup button types `[Relay · test] Reply with PONG.` into the composer and never touches the send button.

How to test (publisher):

1. `npm run build:ext` (already run; `dist/` is committed and in sync with `src/`)
2. `chrome://extensions` → Developer mode → **Load unpacked** → select `spikes/chatgpt-extension/` (reload the extension if it was loaded before)
3. Open chatgpt.com with DevTools console visible; send a message — the completed reply must appear as one `[relay-spike]` log with its hash, never mid-stream
4. Ask for one reply containing a code block — check the text survives intact
5. Switch to a different conversation in the sidebar, then reload the tab — old replies must NOT re-log
6. Click the extension's toolbar button → the PONG prompt appears in the composer and waits; you click Send
7. If available, try one reply from a thinking model and check the logged text is the final answer
8. If the page changes again: a conversation URL with zero turns prints `[relay-spike] WARNING: no turns found, selectors may be stale`

Review fixes applied (2026-10-18, review of commit 7307d04 + Chris's live console checks):

1. Selectors replaced with the observed DOM: turn `[data-talvt-turn-state]`, reply body `[data-dil-message-id]`, stop button `form[data-chatgpt-composer] button[aria-label="Stop"]`, composer `form[data-chatgpt-composer] [contenteditable="true"][role="textbox"]` — the page had been rebuilt and none of the original selectors matched, so the spike never saw a reply in live testing.
2. Popup listener crash fixed: the code called `chrome.runtime.addListener` instead of `chrome.runtime.onMessage.addListener` (TypeError on every page — this killed the popup path in live testing).
3. Replies are tracked by `data-dil-message-id`, not a text hash — identical replies (PONG twice) now each log; the sha256 stays in the log line as the SPEC fingerprint.
4. Old replies no longer log as new: eligibility requires witnessing the reply stream (turn `in_progress` or stop button seen) during this page session — the old "no stop button right now" state check failed reloads and sidebar switches. The seed-on-load step is gone; witnessing replaces it.
5. Loud failure added: zero turns on a conversation URL logs one `WARNING: no turns found, selectors may be stale`, because `data-talvt-turn-state` looks internal and may be renamed again.

Re-review fixes (the text-memory guard, applied 2026-10-18):

6. The stability watch is keyed by `data-dil-message-id` and cleared after logging — the previous code compared reply text alone, so a second identical reply (PONG twice) was skipped, silently undoing fix 3.
7. The stability timer re-arms while the turn is not yet `complete`, so a reply can no longer be silently dropped when the turn is marked complete a moment late.
8. The MutationObserver also watches `data-talvt-turn-state` attribute flips, so a late completion is evaluated immediately instead of waiting for the next DOM change.

Deliberate deviation (per review): `sendButton` is defined in `selectors.ts` but unused — the send button is not present while the composer is empty (a Dictate button shows instead), so completion is judged by the stop button disappearing, turn state, and text stability. The M1.4 adapter can adopt the send button when it exists.

Files changed: `spikes/chatgpt-extension/` (manifest.json, popup.html, build.mjs, src/selectors.ts, src/content.ts, src/popup.ts, dist/content.js, dist/popup.js), `package.json` (+esbuild devDependency, +`build:ext` script), `docs/status/m0.2.md`. `npm test` still 13/13 after every change.

Surprises:

- ChatGPT rebuilt its page: the long-standing `data-message-author-role` / `data-testid` attributes are gone. Live DOM observation (Chris's console) is the only reliable source for these selectors; agent probing of the logged-out shell sees a different composer entirely.
- The listener bug (item 2) shipped because esbuild strips types without type-checking — a wrong type cast hid a wrong property access. Worth a `tsc --noEmit` pass in M1.4.
- MV3 content scripts cannot use ES modules, so the spike needs the small esbuild bundling step; `dist/` is committed so the extension loads without building — rebuild it before every commit that touches `src/` (or stop committing `dist/` in M1.4).
- npm blocked esbuild's postinstall script; the build works regardless and behaves the same on a fresh clone. Approving the script is a publisher security decision (left blocked).
